## 구현 결정 (2026-11-02 Claude 추가 — 여기 적힌 대로 하고, 바꿔야 하면 메모에 이유를 적고 질문한다)
1. **파일:** 실행기는 `src/core/runner/`(공개 API는 `index.ts`, 문구는 `strings.ko.ts`), 테스트는 `src/core/runner/__tests__/`.
2. **엔진 계약 보강(`src/core/engine-sdk/types.ts`, 모두 선택 필드 — 기존 엔진은 그대로 동작):**
   - `emit?(prev: State, next: State, action: Action): EngineEvent[]` — 순수 함수. 러너가 reduce 직후 호출한다. `EngineEvent = { name: string; payload?: JsonValue }`, `name`은 `events` 목록 중 하나여야 한다(개발 모드에서 검사).
   - `receive?(state: State, event: EngineEvent, config: Config): Action | null` — 순수 함수. 다른 엔진의 이벤트를 이 엔진의 Action으로 바꾼다. null이면 무시.
   - `predicates?: Record<string, (observation: Observation, args: JsonValue | undefined) => boolean>` — GoalSpec `predicate`가 이 이름을 찾는다. 없는 이름이면 콘텐츠 검사에서 오류.
   - `docs/02` §3 코드 블록에 같은 내용을 반영한다(docs는 이 절만 수정 가능).
3. **GoalSpec 평가:** `evaluateGoal(goal, observation, engine)`는 순수 함수. `path`는 점 표기(`groups.0`, `count`). `equals`는 JSON 깊은 비교. `equivalent-expr`은 그 경로 값(문자열)을 T002 `equivalent()`로 비교하고, 파싱·계산 오류는 **던지지 않고 false**. 경로가 없으면 false.
4. **콘텐츠 스키마:** `zod`를 dependency로 추가해 `src/core/runner/content-schema.ts`에 둔다. 구조: `{ unit, title, activities: [{ id, title, tasks: [{ id, prompt, engine, mode, cpa, config, goal, hints, concepts, submit: 'auto'|'button' }] }] }`, 과제 ID는 `<활동ID>.T<n>`(예: `g5s1u4.A1.T1`). 여러 엔진 화면(결정 6)은 과제에 `views`와 `links`를 둔다. 스키마 타입은 `engine-sdk`의 `Task`·`GoalSpec`·`HintRule`과 어긋나지 않게 `z.infer` 결과를 타입 테스트로 맞춘다.
5. **콘텐츠 검사:** 모든 `data/content/*.json`을 읽어 스키마 + 참조(unit은 `data/units.json`, concepts는 `data/concepts.json`, engine은 레지스트리, mode는 그 엔진의 `modes`, predicate 이름은 그 엔진의 `predicates`)를 검사하는 테스트 `src/core/runner/__tests__/content-files.test.ts`를 만든다. `package.json`의 `check:specs`를 `node scripts/check-specs.mjs && vitest run src/core/runner/__tests__/content-files.test.ts`로 바꾼다(`scripts/check-specs.mjs`는 고치지 않는다). 예외: unit `demo`는 units.json·concepts 검사를 건너뛴다.
6. **여러 엔진 연결(`linkedViews`):** 과제에 `views: [{ slot, engine, mode, cpa, config }]`(첫 슬롯이 판정 대상)와 `links: [{ from: slot, event, to: slot }]`. 러너가 `from` 슬롯의 `emit` 결과 중 `event` 이름을 `to` 슬롯의 `receive`로 넘기고, 나온 Action을 그 슬롯에 dispatch한다(이것도 Action으로 기록). 연결이 순환하면 같은 Action 처리 안에서 한 번만 전달한다(무한 반복 방지).
7. **기록:** 과제 시작 `started`, 엔진 Action마다 `acted`(`data: { slot, action }`), **되돌리기·다시하기는 `acted`(`data: { slot, control: 'undo'|'redo' }`)**, 제출 `submitted`, 판정 `passed`/`failed`. 통과하면 `taskProgress`를 `completed`로. 로그 저장은 T004 `logEvent`/`Storage`를 쓰고, 저장이 실패해도 수업 화면은 멈추지 않는다(콘솔 경고).
8. **재생:** `replayTask(definition, config, events)`가 위 기록(Action + undo/redo control)만으로 최종 상태를 다시 만든다. 테스트: E00에서 놓기·옮기기·되돌리기·다시하기·묶기를 섞은 기록을 재생하면 화면의 최종 상태·Observation과 같다.
9. **제출과 실패:** `submit: 'auto'`는 Action마다 판정해 참이 되는 순간 통과. `'button'`은 버튼을 눌렀을 때만 판정. 실패해도 **정답·정답 상태를 보여 주지 않고** `strings.ko.ts`의 "다시 볼까?" 계열 문구만 보여 준다. 과제별 실패 횟수를 상태로 들고 있다가 T012 힌트 엔진이 쓰게 공개한다(힌트 선택·표시는 이 카드 범위 밖).
10. **실행 화면(E2E용):** `src/app/`에 URL 해시 `#/run/<unitId>`(예: `#/run/demo`)이면 `data/content/<unitId>.json`을 불러 실행하는 최소 화면을 둔다. 학습자는 아직 선택 화면이 없으므로 예약 ID `"0"`(시연·점검용)으로 기록하고, T006에서 실제 번호 선택으로 바꾼다.
11. **E00 보강:** E00에 `emit`(`counter-added`, `counter-moved`, `grouped`, `ungrouped`)과 `receive`(`counter-added` 받으면 셈돌 하나 놓기), `predicates`(`has-group-of`: args `{ size }`인 묶음이 있는가)를 추가해도 된다. `data/content/demo.json`의 과제 3개: ① 셈돌 5개 놓기(auto, equals `count`) ② 3개짜리 묶음 만들기(button, predicate `has-group-of`) ③ 두 판 연결(views 2개 + link): 왼쪽에 놓으면 오른쪽에도 놓인다, 오른쪽이 4개가 되면 통과.
12. **T002 남은 문제:** `src/core/math`의 `solveForBox`에서 `0 ÷ □ = 0`은 `INFINITE_SOLUTIONS`, `5 ÷ □ = 0`은 `NO_SOLUTION`이 되게 고치고 두 경우 테스트를 추가한다(T002 메모 참고). `src/core/math`에서 고칠 것은 이것뿐이다.
